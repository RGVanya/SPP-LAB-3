# Менеджер задач (СПП, ЛР №2–3) — Конституция

## Core Principles

### I. Безопасность по умолчанию (Secure by Default)

- Каждый маршрут `/api/**`, кроме явно перечисленных публичных (здоровье сервиса, вход,
  регистрация, обновление ключа, восстановление пароля), MUST требовать действующий
  временный ключ доступа.
- Права проверяются на сервере на каждом запросе; скрытие кнопок в интерфейсе — только удобство,
  а не защита.
- Пароли и одноразовые токены MUST храниться только в виде необратимых хешей
  (пароли — с солью и медленной KDF, токены — SHA-256).
- Ответы сервера MUST NOT раскрывать, существует ли учётная запись (вход, восстановление пароля).
- Секреты (ключи подписи, пароли SMTP/БД) задаются только переменными окружения.

**Почему**: лабораторная оценивает именно модель доступа и защиту; ошибка «забыли закрыть
маршрут» должна быть невозможна по построению (deny-by-default).

### II. Семантика HTTP — контракт API

- Коды ответов MUST соответствовать RFC 9110: 200/201/202/204 — успех,
  400 — синтаксически неверный запрос, 401 — нет или недействителен ключ
  (с заголовком `WWW-Authenticate`), 403 — недостаточно прав, 404, 405 (с `Allow`), 409,
  413, 415, 422 — семантически неверные данные, 429 (с `Retry-After`), 500, 503.
- Тело любой ошибки MUST быть `application/problem+json` по RFC 9457
  (`type`, `title`, `status`, `detail`, `instance`) с расширениями `requestId` и `fields`.
- Создание ресурса возвращает `201` и заголовок `Location`.
- Внутренние детали (стек, SQL) MUST NOT попадать в ответ клиенту.

**Почему**: единый предсказуемый формат ошибок упрощает клиент и проверку лабораторной.

### III. Наблюдаемость через структурированные логи

- Все логи сервера MUST быть JSON-строками (одна запись — одна строка) с полями `level`, `time`,
  `msg`, а для запросов — `reqId`, `userId`, `method`, `url`, `statusCode`, `responseTime`.
- Каждому запросу присваивается идентификатор корреляции (`X-Request-Id`), который возвращается
  клиенту в заголовке и в теле ошибки.
- Значимые события безопасности (вход, неудачный вход, блокировка, отзыв сеанса, сброс пароля,
  смена роли) MUST логироваться отдельной записью с полем `event`.
- Пароли, токены, cookie и заголовок `Authorization` MUST маскироваться (redaction).

**Почему**: по логу должно быть можно восстановить «кто, что, когда и с каким результатом».

### IV. Тесты на поведение API (NON-NEGOTIABLE)

- Каждое требование безопасности и каждый код ответа из контракта MUST быть покрыт
  интеграционным тестом против настоящей PostgreSQL.
- Сначала тест, затем реализация (Red → Green → Refactor).
- Внешние побочные эффекты (почта) подменяются через внедрение зависимостей, а не моками модулей.

**Почему**: безопасность нельзя проверить «на глаз»; тесты — доказательство для защиты работы.

### V. Простота и сохранение архитектуры ЛР №2

- Новый код следует существующей слоистой схеме: routes → middlewares → controllers →
  services → repositories, сборка зависимостей — в `container.js`.
- Новая зависимость допустима, только если её нельзя разумно заменить стандартной
  библиотекой Node.js (например, хеширование паролей — встроенный `crypto.scrypt`).
- Никаких спекулятивных функций сверх задания.

**Почему**: работа — дополнение ЛР №2, а не переписывание; проверяющему важно видеть преемственность.

### VI. Понятный и аккуратный интерфейс

- Клиент MUST информативно показывать каждую ошибку на русском языке, включая оставшееся
  время блокировки при 429 и причину отказа при 403.
- Истечение ключа доступа MUST обрабатываться прозрачно (тихое обновление) — пользователь
  не должен терять работу из-за 15-минутного срока жизни ключа.
- Новые экраны используют существующую дизайн-систему (`styles.css`, токены `--c-*`).

**Почему**: «максимально красиво» — требование заказчика; безопасность не должна ломать UX.

## Технологические ограничения

- Сервер: Node.js 22, Express 5, PostgreSQL 17 (`pg`), CommonJS.
- Клиент: React 19 + React Router 7 + Vite, SPA без перезагрузки страницы.
- Развёртывание: Docker Compose; все сервисы (БД, API, почтовый сервер для разработки)
  поднимаются одной командой `docker compose up --build`.
- Схема БД применяется идемпотентным `schema.sql` при старте сервера.

## Процесс разработки и контроль качества

- Работа ведётся по Spec Kit: constitution → specify → clarify → plan → tasks → analyze → implement.
- Готовность фичи: все тесты `npm test` зелёные, клиент собирается `npm run build`,
  `docker compose up --build` поднимает работающее приложение, сценарии из `quickstart.md`
  воспроизводятся вручную.
- Любое отступление от принципов фиксируется в разделе Complexity Tracking плана с обоснованием.

## Governance

- Конституция имеет приоритет над остальными практиками проекта.
- Изменения принимаются правкой этого файла с увеличением версии по SemVer:
  MAJOR — удаление/переопределение принципа, MINOR — новый принцип или раздел,
  PATCH — уточнение формулировок.
- Каждый план (`plan.md`) MUST содержать раздел Constitution Check с проверкой всех принципов.
