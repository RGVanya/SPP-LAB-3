# Feature Specification: Модель доступа, защита учётных записей и наблюдаемость

**Feature Branch**: `001-auth-access-control`

**Created**: 2026-11-06

**Status**: Implemented

**Input**: User description: "Дополнить приложение из лабораторной работы №2:
1) реализовать модель доступа к системе как минимум с 3 ролями на основе временных ключей;
2) реализовать обработку ошибок и кодов возврата в соответствии с семантикой стандартов HTTP;
3) внедрить механизм защиты от подбора учётных данных, контроль активных подключений и
восстановление доступа через электронную почту;
4) реализовать структурированное логирование."

## Clarifications

### Session 2026-11-06

- Q: Какие роли и какие у них права? → A: Три роли с вложенными правами:
  **Наблюдатель** (`viewer`) — просмотр задач и скачивание вложений;
  **Редактор** (`editor`) — всё, что наблюдатель, плюс создание, изменение, удаление задач и вложений;
  **Администратор** (`admin`) — всё, что редактор, плюс управление ролями пользователей,
  просмотр и принудительное завершение сеансов любого пользователя.
  Задачи общие для всей команды (без владельца), чтобы роли были единственным механизмом
  разграничения.
- Q: Какую роль получает пользователь, зарегистрировавшийся самостоятельно? → A: `viewer`
  (принцип минимальных привилегий). Повышает роль администратор. Первый администратор
  создаётся при старте сервера из переменных окружения.
- Q: Что значит «временный ключ»? → A: Короткоживущий подписанный ключ доступа (15 минут),
  предъявляемый с каждым запросом, плюс долгоживущий одноразовый ключ обновления (7 дней),
  который хранится в защищённой cookie и меняется при каждом использовании.
- Q: Порог блокировки при подборе пароля? → A: 5 неудачных попыток для одного e-mail → блокировка
  этого e-mail на 15 минут; 20 неудачных попыток с одного IP-адреса → блокировка IP на 15 минут.
  Блокировка снимается автоматически по истечении времени или после успешного сброса пароля.
- Q: Сколько одновременных сеансов разрешено? → A: Не более 5 активных сеансов на пользователя;
  при входе с 6-го устройства самый старый сеанс завершается автоматически.
- Q: Срок жизни ссылки восстановления пароля? → A: 30 минут, одноразовая; новая ссылка
  аннулирует предыдущие.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Вход в систему и работа в рамках своей роли (Priority: P1)

Сотрудник регистрируется или входит по e-mail и паролю и работает с задачами в пределах прав
своей роли. Наблюдатель видит задачи, но не может их менять; редактор управляет задачами;
администратор дополнительно управляет пользователями. Без входа доступ к задачам закрыт.
Сеанс продлевается незаметно, пока пользователь активен.

**Why this priority**: без аутентификации и ролей не имеет смысла ни один другой пункт задания;
это ядро «модели доступа на основе временных ключей».

**Independent Test**: зарегистрировать нового пользователя, убедиться, что он видит список задач
без кнопок изменения, а попытка изменить задачу напрямую отклоняется; войти редактором и создать
задачу; войти администратором и повысить наблюдателя до редактора.

**Acceptance Scenarios**:

1. **Given** гость без входа, **When** он открывает список задач, **Then** система требует войти
   и не отдаёт данные задач.
2. **Given** новый посетитель, **When** он регистрируется с корректными e-mail и паролем,
   **Then** учётная запись создаётся с ролью «Наблюдатель» и он сразу оказывается в системе.
3. **Given** наблюдатель в системе, **When** он пытается создать, изменить или удалить задачу или
   вложение, **Then** система отказывает с пояснением «недостаточно прав», данные не меняются.
4. **Given** редактор в системе, **When** он создаёт, меняет, удаляет задачи и вложения,
   **Then** операции выполняются как в ЛР №2.
5. **Given** администратор, **When** он меняет роль пользователя, **Then** новые права действуют
   для этого пользователя со следующего же запроса, без повторного входа.
6. **Given** пользователь в системе 20 минут без перезагрузки страницы, **When** он выполняет
   действие после истечения срока ключа доступа, **Then** действие выполняется без повторного
   ввода пароля (ключ обновлён автоматически).
7. **Given** пользователь нажал «Выйти», **When** кто-либо пытается использовать его прежний ключ
   обновления, **Then** система отказывает.
8. **Given** неверная пара e-mail/пароль, **When** выполняется вход, **Then** сообщение одинаково
   для несуществующего e-mail и неверного пароля.

### User Story 2 — Корректные коды ответов и понятные ошибки (Priority: P1)

Любой клиент API (SPA, curl, Postman) получает коды ответов в строгом соответствии со смыслом
стандарта HTTP и единообразное машиночитаемое описание ошибки с человекочитаемым текстом
на русском. Интерфейс показывает эти тексты пользователю.

**Why this priority**: прямое требование задания; затрагивает все существующие маршруты ЛР №2.

**Independent Test**: серией запросов к API получить каждый из кодов 400, 401, 403, 404, 405, 409,
413, 415, 422, 429 и проверить формат тела ошибки и обязательные заголовки.

**Acceptance Scenarios**:

1. **Given** запрос без ключа к защищённому ресурсу, **When** он выполняется, **Then** ответ 401 и
   заголовок с указанием схемы аутентификации.
2. **Given** ключ с недостаточной ролью, **When** выполняется запрос, **Then** ответ 403.
3. **Given** тело запроса — некорректный JSON, **When** он отправлен, **Then** ответ 400.
4. **Given** корректный JSON с недопустимыми значениями полей, **When** он отправлен,
   **Then** ответ 422 с перечнем ошибок по полям.
5. **Given** тело не в JSON (например, `text/plain`) для JSON-ресурса, **When** отправлено,
   **Then** ответ 415.
6. **Given** существующий адрес и неподдерживаемый метод, **When** запрос выполнен, **Then** ответ
   405 и список допустимых методов.
7. **Given** регистрация с уже занятым e-mail, **When** отправлена, **Then** ответ 409.
8. **Given** успешное создание задачи, **When** ответ получен, **Then** статус 201 и адрес нового
   ресурса.
9. **Given** любая ошибка, **When** ответ получен, **Then** в нём есть идентификатор запроса,
   по которому запись находится в журнале сервера.
10. **Given** непредвиденный сбой сервера, **When** ответ получен, **Then** статус 500 без
    технических подробностей; если недоступна БД — 503.

### User Story 3 — Защита от подбора пароля (Priority: P2)

Злоумышленник, перебирающий пароли, быстро упирается во временную блокировку. Пользователь
видит, через сколько можно повторить попытку.

**Why this priority**: часть пункта 3 задания; критично для безопасности, но опирается на US1.

**Independent Test**: 5 раз ввести неверный пароль для одного e-mail — 6-я попытка (даже с верным
паролем) отклоняется с указанием времени ожидания; через 15 минут вход снова возможен.

**Acceptance Scenarios**:

1. **Given** 4 неудачные попытки для e-mail, **When** 5-я попытка неудачна, **Then** e-mail
   блокируется на 15 минут.
2. **Given** заблокированный e-mail, **When** вводится даже верный пароль, **Then** ответ
   «слишком много попыток» и время до разблокировки; интерфейс показывает обратный отсчёт.
3. **Given** несуществующий e-mail, **When** по нему перебирают пароли, **Then** поведение
   идентично существующему (блокировка тоже наступает) — нельзя узнать, есть ли такой e-mail.
4. **Given** 3 неудачные попытки, **When** 4-я попытка успешна, **Then** счётчик обнуляется.
5. **Given** 20 неудачных попыток с одного IP по разным e-mail, **When** следует 21-я,
   **Then** IP блокируется на 15 минут.
6. **Given** частые запросы восстановления пароля с одного IP, **When** превышено 5 запросов за
   15 минут, **Then** следующие отклоняются как «слишком много запросов».

### User Story 4 — Контроль активных сеансов (Priority: P2)

Пользователь видит список устройств, где выполнен вход (браузер, IP, время входа и последней
активности), и может завершить любой сеанс или все, кроме текущего. Администратор видит активные
сеансы всех пользователей и может принудительно завершить любой.

**Why this priority**: часть пункта 3 задания («контроль активных подключений»).

**Independent Test**: войти в двух браузерах, в первом завершить сеанс второго — во втором
следующий запрос приводит к выходу на страницу входа.

**Acceptance Scenarios**:

1. **Given** вход с двух устройств, **When** пользователь открывает «Мои сеансы», **Then** видит
   оба, текущий помечен.
2. **Given** пользователь завершил чужой (свой другой) сеанс, **When** то устройство делает
   следующий запрос, **Then** доступ отклонён немедленно, без ожидания истечения ключа.
3. **Given** 5 активных сеансов, **When** выполняется 6-й вход, **Then** самый старый сеанс
   завершается автоматически.
4. **Given** «Завершить все другие», **When** выполнено, **Then** остаётся только текущий сеанс.
5. **Given** администратор, **When** он завершает сеанс другого пользователя, **Then** тот
   теряет доступ со следующего запроса; не-администратору эта функция недоступна (403).
6. **Given** обнаружено повторное использование уже использованного ключа обновления (признак
   кражи), **When** это происходит, **Then** весь соответствующий сеанс завершается.

### User Story 5 — Восстановление доступа через e-mail (Priority: P2)

Пользователь, забывший пароль, запрашивает ссылку на почту, переходит по ней и задаёт новый
пароль. После смены пароля все его сеансы завершаются, а на почту приходит уведомление.

**Why this priority**: часть пункта 3 задания.

**Independent Test**: запросить восстановление, открыть письмо в почтовом ящике разработки,
перейти по ссылке, задать новый пароль, войти с ним; старый пароль не работает.

**Acceptance Scenarios**:

1. **Given** любой e-mail (зарегистрированный или нет), **When** запрошено восстановление,
   **Then** ответ одинаковый: «если адрес зарегистрирован, письмо отправлено».
2. **Given** зарегистрированный e-mail, **When** запрошено восстановление, **Then** приходит
   письмо со ссылкой, действующей 30 минут.
3. **Given** действующая ссылка, **When** задан новый пароль, **Then** пароль меняется, ссылка
   становится недействительной, все сеансы пользователя завершаются, блокировка e-mail снимается,
   приходит письмо-уведомление о смене пароля.
4. **Given** просроченная, использованная или поддельная ссылка, **When** по ней задают пароль,
   **Then** отказ с понятным сообщением и предложением запросить новую.
5. **Given** запрошены две ссылки подряд, **When** используется первая, **Then** она недействительна.

---

### User Story 6 — Структурированный журнал событий (Priority: P3)

Администратор/разработчик анализирует работу сервиса по журналу: каждая запись — одна строка
машиночитаемого формата с уровнем, временем, идентификатором запроса и пользователя; события
безопасности выделены отдельно; секреты в журнал не попадают.

**Why this priority**: пункт 4 задания; не влияет на функциональность для пользователя.

**Independent Test**: выполнить вход, неудачный вход и запрос к задаче, затем отфильтровать журнал
контейнера по идентификатору запроса и по полю события.

**Acceptance Scenarios**:

1. **Given** любой HTTP-запрос, **When** он завершён, **Then** в журнале одна запись с методом,
   адресом, статусом, длительностью, идентификатором запроса и (если есть) пользователя.
2. **Given** событие безопасности (вход, неудачный вход, блокировка, выход, завершение сеанса,
   повторное использование ключа, запрос и выполнение сброса пароля, смена роли),
   **When** оно произошло, **Then** в журнале есть запись с типом события.
3. **Given** запрос с паролем или ключом, **When** он записан в журнал, **Then** значения секретов
   замаскированы.
4. **Given** клиент передал собственный идентификатор запроса, **When** запрос обработан,
   **Then** этот идентификатор используется в журнале и возвращается в ответе.
5. **Given** ошибка 5xx, **When** она произошла, **Then** в журнале есть уровень `error` и
   подробности (стек), которых нет в ответе клиенту.

---

### Edge Cases

- Ключ доступа подписан другим секретом, искажён или просрочен → 401 с указанием
  `invalid_token`; клиент пытается один раз обновить ключ, при неудаче — выход на страницу входа.
- Пользователя заблокировали/понизили, пока у него открыта страница → со следующего запроса
  действуют новые права (403 вместо успеха).
- Администратор пытается понизить собственную роль → 409, чтобы система не осталась без
  администратора.
- Одновременно два запроса обновления с одним ключом (две вкладки) → второй распознаётся как
  повторное использование; клиент сериализует обновления в одной вкладке.
- Письмо не отправилось (почтовый сервер недоступен) → пользователю всё равно 202 (не раскрываем
  наличие учётной записи), в журнале — ошибка с подробностями.
- Пароль короче 8 символов или длиннее 128 → 422 с указанием поля.
- E-mail вводится в разном регистре → считается одним и тем же адресом.
- Скачивание вложения тоже требует ключа и роли не ниже наблюдателя.
- Запрос к несуществующему адресу API → 404 в формате ошибки; к адресу SPA → отдаётся интерфейс.

## Requirements *(mandatory)*

### Functional Requirements

**Модель доступа (п. 1)**

- **FR-001**: Система MUST поддерживать регистрацию по e-mail, имени и паролю
  (8–128 символов); самостоятельно зарегистрированный пользователь получает роль `viewer`.
- **FR-002**: Система MUST аутентифицировать пользователя по e-mail и паролю и выдавать
  временный ключ доступа со сроком жизни 15 минут и ключ обновления со сроком жизни 7 дней.
- **FR-003**: Ключ обновления MUST быть одноразовым: при каждом обновлении выдаётся новая пара,
  старый ключ становится недействительным.
- **FR-004**: Система MUST поддерживать три роли с вложенными правами: `viewer` ⊂ `editor` ⊂
  `admin` (матрица прав — в Clarifications).
- **FR-005**: Все маршруты задач и вложений MUST требовать действующий ключ доступа; чтение —
  роль не ниже `viewer`, изменение — не ниже `editor`.
- **FR-006**: Администратор MUST иметь возможность просматривать список пользователей и менять
  их роли; изменение роли действует со следующего запроса.
- **FR-007**: Первый администратор MUST создаваться при старте системы из параметров окружения,
  если такого пользователя ещё нет.
- **FR-008**: Пользователь MUST иметь возможность выйти; выход завершает текущий сеанс.

**Ошибки и коды ответов (п. 2)**

- **FR-010**: Все ошибки API MUST возвращаться в едином формате «Problem Details» (RFC 9457) с
  типом, заголовком, статусом, подробностью на русском, адресом запроса, идентификатором запроса
  и (для ошибок валидации) перечнем ошибок по полям.
- **FR-011**: Коды ответов MUST соответствовать таблице: 400 — синтаксически неверный запрос
  (битый JSON); 401 — нет/недействителен ключ или неверные учётные данные (с заголовком
  аутентификации); 403 — недостаточно прав; 404 — ресурс не найден; 405 — метод не поддерживается
  (с перечнем допустимых); 409 — конфликт состояния (занятый e-mail, понижение себя);
  413 — слишком большое тело/файл; 415 — неподдерживаемый тип содержимого; 422 — ошибки
  валидации; 429 — превышен лимит (со временем ожидания); 500 — внутренняя ошибка;
  503 — временно недоступна зависимость.
- **FR-012**: Успешное создание MUST возвращать 201 и адрес нового ресурса; асинхронно
  принятый запрос (восстановление пароля) — 202; успешное удаление/действие без тела — 204.
- **FR-013**: Ответ клиенту MUST NOT содержать стек вызовов, SQL или иные внутренние детали.
- **FR-014**: Интерфейс MUST показывать текст каждой ошибки; ошибки полей — рядом с полями.

**Защита и сеансы (п. 3)**

- **FR-020**: Система MUST блокировать вход для e-mail на 15 минут после 5 неудачных попыток
  подряд и для IP-адреса — после 20 неудачных попыток; во время блокировки отвечать 429 с
  временем ожидания, даже при верном пароле.
- **FR-021**: Учёт попыток MUST вестись одинаково для существующих и несуществующих e-mail;
  время ответа на неверный e-mail MUST быть сопоставимо со временем на неверный пароль.
- **FR-022**: Успешный вход MUST обнулять счётчик неудачных попыток для e-mail.
- **FR-023**: Запросы восстановления пароля MUST ограничиваться 5 запросами за 15 минут с IP.
- **FR-024**: Каждый вход MUST создавать сеанс с данными об устройстве (браузер), IP, временем
  создания и последней активности; у пользователя не более 5 активных сеансов, при превышении
  завершается самый старый.
- **FR-025**: Пользователь MUST видеть свои активные сеансы, завершать любой из них или все,
  кроме текущего.
- **FR-026**: Администратор MUST видеть активные сеансы всех пользователей и завершать любой.
- **FR-027**: Завершённый сеанс MUST терять доступ немедленно — со следующего запроса, даже если
  срок ключа доступа ещё не истёк.
- **FR-028**: Повторное использование ключа обновления MUST завершать весь сеанс и
  фиксироваться как событие безопасности.
- **FR-029**: Пользователь MUST иметь возможность запросить ссылку восстановления пароля на
  e-mail; ответ одинаков для любых адресов.
- **FR-030**: Ссылка восстановления MUST быть одноразовой, действовать 30 минут; выдача новой
  ссылки аннулирует прежние.
- **FR-031**: Смена пароля по ссылке MUST завершать все сеансы пользователя, снимать блокировку
  e-mail и отправлять письмо-уведомление.

**Логирование (п. 4)**

- **FR-040**: Сервер MUST писать журнал в машиночитаемом формате «одна запись — одна строка» с
  уровнем, временем и сообщением.
- **FR-041**: Каждый HTTP-запрос MUST порождать запись с идентификатором запроса, методом,
  адресом, статусом, длительностью и идентификатором пользователя (если вошёл).
- **FR-042**: Идентификатор запроса MUST приниматься от клиента (если корректен) или
  генерироваться и возвращаться в заголовке ответа.
- **FR-043**: События безопасности (перечень — в US6) MUST записываться отдельными записями
  с типом события.
- **FR-044**: Пароли, ключи, cookie и заголовок авторизации MUST маскироваться в журнале.
- **FR-045**: Уровень детализации журнала MUST настраиваться параметром окружения.

### Key Entities

- **Пользователь**: e-mail (уникален без учёта регистра), имя, хеш пароля, роль, дата
  регистрации, дата смены пароля.
- **Сеанс**: принадлежит пользователю; хеш текущего ключа обновления, браузер, IP, время
  создания, последней активности, истечения, время и причина завершения.
- **Ограничитель попыток**: ключ (e-mail или IP + назначение), число неудач, время первой
  неудачи окна, время окончания блокировки.
- **Токен восстановления пароля**: принадлежит пользователю; хеш, срок действия, время
  использования.
- **Задача, Вложение**: без изменений относительно ЛР №2.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100 % маршрутов задач и вложений недоступны без входа (проверяется тестами на
  каждый маршрут).
- **SC-002**: Каждая из 3 ролей получает отказ ровно на тех операциях, которые запрещены
  матрицей прав, и успех на разрешённых (проверка всей матрицы тестами).
- **SC-003**: Пользователь, активно работающий 1 час, ни разу не вводит пароль повторно.
- **SC-004**: Подбор пароля ограничен не более чем 5 попытками на учётную запись за 15 минут.
- **SC-005**: Завершённый сеанс теряет доступ на первом же следующем запросе (0 успешных
  запросов после завершения).
- **SC-006**: Пользователь восстанавливает доступ через e-mail менее чем за 2 минуты.
- **SC-007**: Для любого ответа с ошибкой по его идентификатору находится ровно одна запись
  запроса в журнале.
- **SC-008**: Ни одна запись журнала не содержит пароль или ключ в открытом виде.
- **SC-009**: Все 12 кодов ошибок из FR-011 воспроизводимы и имеют единый формат тела.

## Assumptions

- Пользователи работают из современного браузера с включёнными cookie.
- Для разработки и защиты лабораторной используется локальный почтовый сервер с веб-интерфейсом
  (письма не уходят в интернет); в продакшене достаточно указать параметры реального SMTP.
- Подтверждение e-mail при регистрации, двухфакторная аутентификация, OAuth/SSO и смена пароля
  из профиля — вне рамок задания.
- Приложение работает за одним экземпляром сервера; распределённое хранилище лимитов не нужно,
  состояние лимитов хранится в БД.
- IP-адрес клиента определяется по прямому подключению (без доверия заголовкам прокси), если не
  настроено иное.
- Демонстрационные учётные записи редактора и наблюдателя создаются вместе с администратором
  для удобства проверки лабораторной.
